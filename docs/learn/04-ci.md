# 04 — Continuous integration

*Phase 0, unit 5. Covers the curriculum bullet "CI: what a runner is, why lint and test gate
a merge".*

## Brief

**What is it?** CI is a service that runs your checks on a fresh machine every time you
push, and reports pass or fail against the commit.

The name is older than the tooling. "Continuous integration" originally described a
*practice*: merge small changes into a shared main branch constantly, rather than
disappearing onto a branch for two months and discovering at merge time that four people
rewrote the same file. The tooling grew up to support it — if you are merging constantly,
you need constant automatic proof that main still works. Today most people say "CI" and mean
the tooling.

**What problem does it solve?** Two, and they are different.

*"Works on my machine."* Your machine has a Go toolchain installed in March, a Postgres
configured once and forgotten, environment variables set in a shell you do not remember
opening, and files that never got committed. A test passing there proves less than it
appears to. A runner starts from a known image, clones only what is actually committed, and
runs the checks. Pass there and it passes for a stranger. This is the same problem
containers solve, aimed at verification instead of deployment.

*Humans skip checks.* Not from laziness — you are fixing a one-line typo at 6pm and running
the full suite feels absurd. That is precisely when things break. Gating the merge on
automated checks removes the judgment call entirely.

Before CI, you ran tests when you remembered, main broke regularly, and someone was
informally responsible for noticing. Nightly build servers were the intermediate step: they
told you at 9am that something from yesterday afternoon was broken, by which point three
more changes had landed on top of it.

**How does it work underneath?** A **runner** is a virtual machine that GitHub boots for
your job from a standard image. It checks out your repository at the pushed commit, executes
the steps you listed, reports the result, and is then destroyed. Every run is a fresh
machine — that is the whole value, and it is also why anything not committed simply does not
exist there.

A **workflow** is a YAML file in `.github/workflows/`. It declares **triggers** (on push, on
pull request), one or more **jobs**, and each job's **steps**. Jobs run in parallel on
separate runners; steps inside a job run in sequence on the same one.

**Service containers** are the piece that matters most here. A job can declare containers to
start alongside it — a real Postgres — reachable on localhost. That is how you test against
an actual database instead of a mock.

**Sharp edges.**

- **The runner is not your machine.** Linux, not Windows: case-sensitive filesystem, LF line
  endings, cgo available. Things that pass locally fail there for environmental reasons.
  That is the point, and it still surprises people. The `.gitattributes` added in unit 3
  exists precisely because of this.
- **Caching is a correctness risk, not only a speed one.** A stale cache can make CI pass on
  code that would fail from clean.
- **Green CI is necessary, not sufficient.** It proves the checks you wrote pass. It says
  nothing whatsoever about the checks you did not write.
- **Third-party actions run with your repository's permissions.** `uses: someone/action@v1`
  executes a stranger's code in a job that may hold secrets. Pin versions, prefer known
  publishers, and set `permissions:` explicitly rather than inheriting generous defaults.

**In hooklens.** One workflow on push and pull request. A test job with a real Postgres
service container, so migrations are applied and reversed for real on every commit. A lint
job. A Docker build job. And this is where `go test -race` finally runs — the race detector
needs cgo, cgo needs a C compiler, and the Windows development machine has none. Phase 3 is
goroutines around a mutex-guarded map, so it is about to matter a great deal.

## Decisions

**Three jobs, not one.**
Alternative was a single job running lint, test and the Docker build in sequence. Chose to
split them because jobs run in parallel on separate runners, so wall-clock time is the
slowest job rather than the sum — and, more usefully, a red X tells you *which kind* of
thing broke before you open anything. "lint failed" and "docker build failed" are different
problems with different urgency.
*Wrong call if* the jobs shared expensive setup, since each one pays for checkout and
toolchain install separately. They do not.

**A real Postgres service container, not SQLite and not a mock.**
The migrations use `uuidv7()` and a POSIX-regex `CHECK` constraint. Neither exists in
SQLite. Testing against a substitute would verify a *different schema* than the one we
ship, which is worse than not testing it — it produces confident green checkmarks about
something that was never run.
*The signal this was right:* it costs about four seconds of runner time.

**`go-version-file: go.mod` instead of pinning a version in the workflow.**
One place to bump Go, and no way for the workflow and the module to drift apart. A pinned
`go-version: "1.25"` in YAML is a second source of truth that nobody remembers to update.

**`-count=1` on the test run.**
Go caches test results keyed on the inputs. In CI that cache is usually cold, but when it is
not, a "pass" can be reported without executing anything. `-count=1` defeats the cache. It
costs nothing and removes a class of false confidence.

**gofmt check written by hand rather than using a linter for it.**
`gofmt -l` prints misformatted filenames and exits 0 regardless, so the failure has to be
constructed from whether the output is empty. Verified that it actually fails: dropping a
deliberately malformed file in made the check report it. A formatting gate that cannot fail
is worse than no gate, because it is believed.

**`concurrency` with `cancel-in-progress`.**
Pushing three times in a minute otherwise queues three full runs and you wait on results for
commits you have already replaced. *Wrong call for* a workflow that deploys or publishes,
where cancelling half-way could leave something partly released. Safe here — nothing this
workflow does has side effects outside the runner.

**`permissions: contents: read` set explicitly.**
Default token permissions are broader than any job here needs, and every `uses:` line runs
a stranger's code with whatever the job holds. Least privilege costs two lines.

**Migrations tested up → down → up, not just up.**
The down-then-up cycle is what catches a `-- +goose Down` section that was written and never
executed. Applying forward only would have passed even if the Down block were nonsense.

**Docker layer cache via `type=gha`.**
Without it every run re-downloads the entire module graph, which is the layer-ordering point
from unit 3 turned into minutes of runner time. Requires `setup-buildx-action` — the default
Docker builder cannot use the GitHub Actions cache backend.

**Action versions chosen conservatively (`checkout@v4`, `setup-go@v5`,
`golangci-lint-action@v6`).**
These cannot be verified from here: there is no GitHub remote yet, so the workflow has never
run. `actionlint` validates the schema, expressions, and shell, but it cannot confirm that a
given action version exists or that golangci-lint's own major version matches the action's.
Newer majors exist. If anything is red on first push it will be the lint job, and it is
isolated in its own job precisely so it cannot mask the others.

## Walkthrough

### `.github/workflows/ci.yml`

**Triggers** — `push` restricted to `main`, `pull_request` unrestricted. Without the branch
filter, a PR from a branch in the same repository triggers both events and every run is
duplicated.

**`concurrency`** — the group key `${{ github.workflow }}-${{ github.ref }}` scopes
cancellation to one workflow on one branch, so a push to a feature branch never cancels a
run on main.

**`services.postgres`** — `ports: 5432:5432` publishes the container's port onto the
runner's localhost, which is why `DATABASE_URL` says `localhost` and not a container
hostname. The `options:` block is a raw `docker run` argument string; the health flags there
do the same job as the `healthcheck:` block in `compose.yaml`, and GitHub holds the job
until they pass. Delete them and the first migration step races the database — passing most
of the time, which is the worst possible failure rate.

**The gofmt step** is the only multi-line `run:` with real logic. `$(gofmt -l .)` captures
filenames; `[ -n "$unformatted" ]` is true when the string is non-empty; `exit 1` is what
actually fails the job. The `echo`s exist so the log names the files rather than just
turning red.

**`test (race detector)`** — the reason this job runs on Linux at all. `-race` requires cgo,
cgo requires a C compiler, and the Windows development machine has none. This is currently
the only place the detector runs, and from Phase 3 it is the only thing standing between a
data race and a bug that reproduces once a week in production.

**`migrations up / down / up`** — `env:` is scoped to this step rather than the job, so the
DSN is not in scope for steps that have no business connecting to a database.

**The `docker` job** builds but does not push (`push: false`). Building is the check;
publishing an image is Phase 5's problem. `build-args: VERSION=${{ github.sha }}` feeds the
`ARG VERSION` in the Dockerfile, which feeds `-ldflags -X main.version=`, which sets the
`version` variable in `cmd/hooklens/main.go:21` — so every image built by CI knows the exact
commit it came from.

### `README.md`

Deliberately a *working* README, not the product page from PLAN.md's Phase 6. It states the
phase up front so nobody clones it expecting a webhook inspector, and its centrepiece is the
three commands that take a fresh clone to a running server. The two equivalent `curl`
examples exist to make the routing model obvious without reading `routing.go`.

## Verified

- `actionlint` (in a container) reports **no findings**: schema, expression syntax, and
  shellcheck over every `run:` block
- Every CI step run locally against the compose Postgres: gofmt, vet, build, test,
  migrate up/status/down/up — all pass
- The gofmt gate was proven to *fail* by dropping a malformed file in and watching it get
  reported, then removing it
- **Not verified:** the workflow has never executed on GitHub. There is no remote. Action
  versions and the golangci-lint pairing are the untested surface.
